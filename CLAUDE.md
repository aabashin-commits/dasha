# Keyframe — сайт видеопродакшн-студии

Многостраничный статический сайт. Контент хранится в JSON, страницы генерируются скриптом сборки.

Полное ТЗ: `docs/superpowers/specs/2026-08-01-keyframe-site-design.md`

---

## Стек

HTML5 + CSS3 + vanilla JS (ES-модули). Node.js — только на этапе сборки. PHP 8.1+ — только в `public/api/lead.php`.

**Не использовать:** React, Vue, Svelte, jQuery, Bootstrap, Tailwind, SCSS/LESS и любые runtime-зависимости в браузере. Результат сборки — статические HTML/CSS/JS плюс один PHP-файл.

Допустимые dev-зависимости: `esbuild`, `sharp`, `chokidar`. Что-либо ещё — только после согласования.

Vite заменён на esbuild: HTML генерирует наш скрипт, и мирить с этим конвейером Vite дороже, чем собрать бандл одним вызовом esbuild.

---

## Команды

```
npm run dev       # сервер на :4321 + полная пересборка по изменению файла
npm run build     # валидация → ассеты → страницы → sitemap → dist/
npm run validate  # только проверка content/*.json
npm run preview   # просмотр собранного dist/ без пересборки
npm run images    # заглушки в public/media из content/*.json
npm run mock      # Node-мок эндпоинта заявок для проверки формы
```

`node scripts/fetch-fonts.js` — разовая операция: скачивает woff2 и генерирует `src/styles/fonts.css`. Перезапускать только при смене состава гарнитур.

## Архитектура: контент отделён от разметки

`content/*.json` — единственный источник контента. `scripts/build.js` читает JSON, рендерит шаблоны из `src/templates/` и пишет статические HTML в `dist/`.

Добавление кейса = новый объект в `content/works.json`. Страница, мета-теги, микроразметка и запись в `sitemap.xml` появляются автоматически.

**Никогда не хардкодить контент в HTML-шаблоны.** Тексты, цены, названия, контакты — только из JSON. Шаблон описывает структуру, а не содержание.

Клиентский рендер контента из JSON запрещён: он ломает индексацию Яндексом и Open Graph при шаринге. Всё, что должно попасть в индекс, генерируется на сборке.

## Дизайн-система

Все значения — CSS-переменные в `src/styles/tokens.css`. В компонентах использовать только переменные.

**Запрещено:** хардкод цветов (`#fff`, `rgb(...)`), размеры шрифта в px, отступы вне шкалы `--sp-*`, `!important` (единственное исключение — блок `prefers-reduced-motion`), инлайн-стили, `z-index` вне шкалы токенов.

**Акцентный лайм `--lime`** занимает не более ~5% площади экрана — это сигнал, а не фон.

- Разрешён: первичные кнопки, кольцо фокуса, плейхед и активный маркер спайна, номера этапов процесса, активный пункт фильтра, кнопка Play, подчёркивание ссылки на hover.
- Запрещён: заливки секций, длинный текст, фон карточек.
- Текст поверх лайма — всегда `--lime-ink` (тёмный). Лайм на светлом фоне не использовать: контраст 1.2:1.
- Нумерации 01–04 на карточках направлений нет: они параллельны, а не последовательны. Номера только в блоке процесса.

Анимируем только `transform` и `opacity`. Блок `@media (prefers-reduced-motion: reduce)` обязателен. Скролл-джекинг, кастомные курсоры и параллакс на мобильных — не применять.

## Правила кода

- Один компонент = один CSS-файл в `src/styles/components/` + один JS-модуль в `src/scripts/modules/`. Имена совпадают.
- Файл длиннее ~200 строк — делить по ответственности.
- CSS-классы по BEM: `.work-card__title`, `.work-card--featured`.
- JS: ES-модули, каждый экспортирует `init()`. `main.js` только регистрирует модули и сам ничего не делает.
- Модуль проверяет наличие своих элементов на странице и молча выходит, если их нет.
- Никаких глобальных переменных. Где элементов много — делегирование событий.
- Комментарии объясняют «почему», а не «что».

**Три ловушки, на которые уже наступали в прототипе:**

- **Появление секций скрывать только под классом `.js`.** Правило `.reveal{opacity:0}` без этого оставляет пустую страницу при отказе JS. Инлайн-скрипт в начале `<body>` ставит `document.documentElement.classList.add('js')`, стили пишутся как `.js .reveal`.
- **`aspect-ratio` не работает на inline-элементе.** Если обёртка медиа — `<span>` внутри `<a>`, ей нужен `display:block`, иначе высота нулевая и карточка не отрисуется.
- **Проверять имена классов на коллизии.** `.w-b` как размещение в сетке и `.w-b` как подпись карточки — разные вещи с одним именем: правила одного прилетают на другое. Классы раскладки называть отдельным префиксом (`.pos-*`).

## SEO — проверять на каждой странице

Ровно один `<h1>`. Уровни заголовков не пропускаются; визуальный размер задаётся классом, а не выбором тега.

Обязательны: `title` (≤60 символов), `description` (≤160), `canonical`, полный Open Graph с `og:image` 1200×630, JSON-LD по таблице из раздела 8.3 ТЗ.

Изображения: `<picture>` с AVIF → WebP → JPG, обязательные `width` и `height` (защита от CLS), осмысленный `alt` из JSON.

## Безопасность

Секреты — токен Telegram-бота, `TELEGRAM_CHAT_ID`, доступы SMTP, `CRM_WEBHOOK_URL` — только в `public/api/config.php`, который в `.gitignore` и закрыт правилом `.htaccess`. Никогда в клиентском коде и никогда в репозитории.

`lead.php` обязан выполнять все шаги: проверка Origin, honeypot, временная метка, rate limit, валидация и санитизация каждого поля. Валидация на клиенте дублирует серверную, но не заменяет её.

---

## Доступность

Контраст ≥4.5:1 для текста и ≥3:1 для интерактивных элементов. Видимый `:focus-visible`. Полная навигация с клавиатуры. `aria-expanded` на раскрывающихся элементах, `aria-live` на результате формы, фокус-ловушки в мобильном меню и лайтбоксе. Тач-цели ≥44×44px.

## Проверка вёрстки: как не жечь ресурсы

Главный источник потерь при вёрстке — не сложность задачи, а привычка дёргать браузер после каждой строчки CSS. Правила ниже обязательны.

### Один сервер на всю сессию

`npm run dev` запускается **один раз** в фоне и живёт до конца работы. Он сам пересобирает проект при изменении файла в `content/`, `src/`, `public/` или `scripts/` — перезапускать его не нужно никогда.

- Не убивать и не перезапускать сервер после правок.
- Перед запуском проверить, не поднят ли он уже: `lsof -ti:4321`. Если порт занят своим же процессом — переиспользовать.
- Полная пересборка занимает меньше 200 мс, поэтому HMR не нужен: достаточно перезагрузить вкладку.

### Одна вкладка браузера на всю сессию

`browser_navigate` вызывается один раз. Дальше вкладка живёт и переиспользуется.

- **Никогда не вызывать `browser_close` между проверками.** Только когда вёрстка полностью закончена.
- После правки — повторный `browser_navigate` на тот же URL перезагружает страницу. Открывать новую вкладку не нужно.
- Не запускать браузер ради вопроса, на который отвечает `grep` по `dist/`.

### Сначала дешёвые проверки, браузер — последним

Большая часть ошибок ловится без единого пикселя. Порядок такой:

1. `npm run validate` — контент и схемы.
2. `npm run build` — падает на неизвестных переменных в шаблонах и битых путях к медиа.
3. `grep` по `dist/`: количество `<h1>` на страницу, наличие `og:image` и `canonical`, отсутствие пустых `alt`.
4. `grep` по `src/styles/`: хардкод цветов (`#`, `rgb(`), размеры шрифта в `px`, `!important` вне блока `prefers-reduced-motion`.
5. И только теперь браузер — для того, что действительно требует глаз: пропорции, вертикальный ритм, наложения, поведение при hover.

### Верстать секцию целиком, проверять один раз

Не проверять после каждого свойства. Цикл: доверстал секцию → накопил список вопросов к ней → один заход в браузер, где закрываются все сразу.

За один заход снимать все ширины подряд, без переоткрытия вкладки: `browser_resize` 360 → `browser_take_screenshot` → 768 → 1440. Mobile-first: начинать с 360, там вылезает больше проблем.

### `browser_snapshot` дешевле скриншота

Вопрос про структуру, порядок элементов, семантику, `aria`, наличие текста — это `browser_snapshot`, он текстовый. Скриншот только тогда, когда вопрос по-настоящему визуальный: отступы, цвет, наложение, пропорции.

### Консоль и сеть — одним вызовом в конце прохода

`browser_console_messages` вызывается один раз после того, как страница пройдена целиком, а не после каждого клика.

### Что проверять за один проход по секции

- Горизонтальный скролл на 360px (частая причина — фиксированные ширины и длинные слова).
- Длинный заголовок и длинный текст в карточке не ломают сетку.
- Отступы взяты из шкалы `--sp-*`, цвета — из токенов.
- Ровно один `<h1>`, уровни заголовков не пропущены.
- Фокус виден при табуляции, тач-цели ≥44×44px.
- Видео и картинки имеют `width`/`height` — нет скачка вёрстки при загрузке.

### Lighthouse — не на каждом этапе

Полный прогон дорогой. Запускать дважды: один контрольный замер после этапа 3 (главная) и финальный на этапе 9. В промежутке ориентироваться на размеры бандлов и наличие `width`/`height` у медиа.

## Перед коммитом

`npm run validate && npm run build` — обязаны пройти без ошибок и предупреждений.

### Скриншоты: два обязательных шага перед снимком

Полностраничный скриншот врёт дважды, и оба раза это выглядит как поломка вёрстки:

1. **`loading="lazy"`** — картинки ниже первого экрана не грузятся, карточки выходят пустыми. Перед снимком: `document.images.forEach(i => i.loading = 'eager')` и дождаться `onload`.
2. **Масштаб** — страница на 10 000 px ужимается в 5 раз, и тёмные кадры пропадают вовсе. Тёмную вёрстку смотреть только скриншотом вьюпорта после `scrollIntoView()`, не миниатюрой всей страницы.

Плюс `.reveal` — элементы скрыты, пока IntersectionObserver не сработал; при съёмке проставить `.reveal--in` вручную.
